# F174-RNET002 — 원래 관리 subnet affinity 유실

- 심각도: Medium. 수정 전 독립 fault injection으로 확인.
- 대상: `0051d8d6803fd447f7b690dd895a0a928c3c7302` 위 미커밋 첫 라우팅 패치, `internal/connector/provider/openstack/topology.go:160` (새 코드). 검토 도중 SDK wrapper/decode는 작성자가 수정했으므로 이 실행은 그 수정 후, subnet-affinity 수정 전이다.
- SSOT: D18 v5 결정7/8의 별도 직접 관리 SSH, 새 runtime 관리 subnet 지원 조건(IPv4 직접 subnet) 및 operation-local 선택한 subnet 고정.
- 재현: 정상 preflight/Management Port 생성은 subnet `management-subnet`/172.16.8.0/24. Nova 생성 후 두 Management Port GET만 같은 Network/SG/DHCP 정책을 유지하고 다른 subnet `different-management-subnet`/172.16.9.200으로 응답한다.
- 실제 결과: stable control PASS. fault에서는 `changedReads=2 outcome=SUCCEEDED probed="172.16.9.200:22" resources=8`. 기대 거절 assertion FAIL, go exit1.
- 원인: `provisionNICs`가 원래 선택한 subnet을 보존하지 않는다. refresh는 관측한 `FixedIPs[0].SubnetID`를 `verifyManagementPort`의 기대 subnet으로 전달해 자기 자신을 비교한다.
- 영향: 새 지원 조건에 맞지 않는 관리 subnet/address로 SSH readiness를 시도하고 정상 Provision으로 보고할 수 있다. 이는 단위 fault에서 확인한 failclosed 계약 결함이며 실제 cloud drift를 관측했다는 뜻은 아니다.
- 필요한 좁은 수정: 선택한 subnet ID를 operation-local NIC state에 보존하고 refresh에서 그 값과 대조. 같은 응답에서 검증한 주소를 SSH에 사용한다. known Port/Server ID는 부분 실패 목록에 보존.
- 회귀: stable 정상성; Nova 생성 후 다른 subnet/주소 거절과 SSH probe0; 모든 created ID 반환; 같은 subnet에서 정책 옵션 변경도 거절.
- 산출물: [외부 probe](management_subnet_affinity_test.go.txt), [overlay](subnet-affinity-overlay.json), [실행 로그](sdk-decode-before.log.gz).
- 실행: Go1.27.1 Windows, in-process HTTP fake + SSH/startup stub. 실제 OpenStack 또는 외부 네트워크 호출 없음. shared repo 수정 없음.

## 수정 후 독립 재검증

작성자는 원래 선택한 managementSubnetID를 provisionNICs에 보존하고 refresh에서 그 값과 비교하도록 수정했다. 같은 overlay를 10회 실행하여 전체 PASS(exit0). stable control 10회 정상, drift 10회는 SSH probe 없이 UNKNOWN/resources8로 반환했다. [수정 후 로그](subnet-affinity-after.log.gz). 이 finding은 검토한 수정 경계에서 해결됐다. 실환경 route/renew 및 helper timeout 검증은 이 probe의 범위가 아니다.
