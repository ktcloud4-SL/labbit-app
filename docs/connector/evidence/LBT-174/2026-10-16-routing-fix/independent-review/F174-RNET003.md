# F174-RNET003 — 빈 DHCP 옵션의 이름 계약 불일치

심각도: Medium. 범위: 표준 Neutron Provision 생성 요청. 수정 전 root에 보고했고 이후 수정된 요청을 독립 검증했다.

최초 코드의 `internal/connector/provider/openstack/management_network.go` `noManagementRoutes.ToPortCreateMap` 옵션 배열(현재 같은 위치 80–83행)은 `3`, `121`, `249`의 빈 문자열을 전송했다. Neutron API에서 빈 문자열이 허용되는 이름은 정확히 `router`, `classless-static-route` 두 개다. 다른 이름은 nonempty 또는 null만 허용하며, DB helper 역시 다른 이름의 빈값을 저장하지 않는다. `249`/`ms-classless-static-route`의 빈값도 이 계약에 포함되지 않는다.

정확한 최초 관측 위치는 보존한 [first-pass source](first-pass/management_network.go.txt) 64–66행이다. 이후 UnmarshalJSON 추가 등으로 같은 결함 배열이 이동한 실행 revision의 줄번호와 구분한다.

재현: 독립 `TestReviewManagementDHCPRequestUsesNeutronBlankableNames`가 실제 생성 builder의 JSON을 디코딩하면 세 이름 모두 계약을 위반하여 FAIL한다. [수정 전 로그](neutron-request-contract-before.log.gz). 실환경 첫 실행이 생성 리소스 6건 상태에서 실패한 사실과 이 API 계약 결함은 구분한다. reviewer는 실제 API 오류 본문을 확보하지 않았으므로 해당 실행의 유일한 원인으로 단정하지 않는다.

영향: 지원 조건을 통과해도 정상 Port CREATE가 거절되거나 옵션이 유효하게 저장되지 않아 Provision/라우팅 정책이 성립하지 않는다. 필요한 회귀: 실제 wire JSON의 canonical 두 이름, 명시 `""`(null/생략 아님), IPv4, 중복·수치 이름·249 거부, 확인된 created ID ledger 보존, 실제 DHCP boot/renew 적용.

수정 후: canonical 두 이름만 요청하고 249는 지원 검증된 Linux guest 경계로 문서화했다. 독립 `TestReviewCanonicalDHCPRequestWireContract`와 checked-in 관리 DHCP 테스트가 PASS했다. [수정 후 로그](canonical-script-regression.log.gz). 이는 API/wire 검증이며 guest 적용 성공을 의미하지 않는다. 후속 실제 실행에서 관리 default route가 남아 renew 단일 Lab default 검증은 실패했으므로 실제 라우팅 수용은 열려 있다.
