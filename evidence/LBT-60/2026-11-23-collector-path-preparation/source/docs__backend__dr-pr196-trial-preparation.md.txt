## DB 적용·복귀

`schema-readonly.sql`은 `BEGIN READ ONLY`와 짧은 statement/lock timeout을 사용하며 신원·적용 이력·테이블 존재만 조회하고 ROLLBACK한다.
DSN·host/user/name·TLS 검증이 먼저이며 CLI 인자/로그에 credential을 넣지 않는다. 아직 실제 DB에서 실행하지 않았다.
DB의 checksum은 후보 **배포 artifact의 정확 bytes**와 비교한다. Windows checkout CRLF 해시와 Git LF 해시를 혼용하지 않는다.
준비 manifest는 Git blob expected checksum과 working-copy checksum을 구분하며 실제 image 내부 검증은 별도다.

- 12: state/change/boundary 테이블·열린 boundary index 생성.
- 13: Resume INTENT/APPLIED journal·pending unique index 생성.
- 14: Resume APPLIED timestamp NOT NULL 제약 추가. 이전 무효 row가 있으면 실패하며 값을 꾸며 채우지 않는다.
- 15: restriction INTENT/APPLIED journal·pending unique index 생성. init 전에 INTENT를 남기므로 state FK는 없다.

runner는 파일별 transaction+적용 기록을 함께 commit하므로 12/13 성공 후14 실패가 가능하다. 앞선 commit을 전체 rollback됐다고
보고하지 않는다. 이미 적용된 checksum/상태를 재조회하고 담당자가 forward-fix/재개 여부를 판단한다. 전체 공유 DB 복원은
시험과 무관한 데이터까지 되돌릴 수 있으므로 자동 복원하지 않는다. CheckSchema는 additive 최신 migration 기록을 허용하지만
이전 image가 durable 제어를 잃는 문제는 별개다. old image로 단순 rollback하여 Worker가 다시 ACTIVE로 열리는 것을 금지한다.
실제 migration 전 새 backup ARN/시각·복원 대상·담당을 고정하고, 상태/승인 이력이 복원 전으로 사라질 경우 외부 원본과 Provider를
대조하기 전 이전 명령을 재전송하지 않는다. schema guard·journal·UNKNOWN을 정리하려고 삭제하지 않는다.

## 적용 전에 반드시 공유할 변경 묶음

1. 후보 image 게시 위치/tag/digest·내용 검증(게시만으로 현재 Pod는 교체되지 않음).
2. 보호 key/Policy/DSN 경로·목적/TTL·실제 IAM/RBAC 차이, 승인 원본 prefix/보존.
3. 공유 DB read-only 접근 방법과 migration12–15·직전 backup·파일별 중단·복구안.
4. root-app/backend 자동 Sync 동결 범위·시간·원래 spec, 선택 Sync의 PreSync migration 실행 여부.
5. maintenance closed의 신규 Provision/Reset/Cleanup 제한, durable init/Pause·APPROVED_CONTROL·Pod 교체/binding.

현재와 같은 `open`+local Worker 상태에서 postgres/APPROVED_CONTROL을 바로 켜지 않는다. init PAUSE_NEW row와 전체 serving Pod
정산·권한·관측이 선행돼야 한다. closed만으로 APPROVED_CONTROL Worker가 멈추지 않는다. 기존 #194 MAINTENANCE 회귀와
#196 APPROVED_CONTROL 시험을 서로 다른 설정/RUN으로 구분한다. 전체 backlog에 영향을 주는 제어이므로 전용 Operation ID만
선별해 실행하는 기능처럼 취급하지 않는다.

작업창의 사용자 부재·전용 조직/Class/VM·실제 Provider 사용 상한·drain timeout은 아직 미확정이다. 가용 시간·비용을 임의로
승인값으로 채우지 않는다. M194-01~06/M196-01~04 기대 결과는 기존 통합 검증 문서를 재사용하되 실제로 실행한 행만 판정한다.
claim 후 dispatch 전의 경쟁 정지점이나 응답유실을 운영에 강제로 주입하는 시험은 별도 영향 검토가 필요하다.

ACTIVE 재개는 fresh signed SingleWriter/Fencing/전체 inventory·PodCoverage·WorkReconciled가 필요하다. SQL0/오사카 replica/현재
서울 primary라는 사실만으로 누락 proof를 PASS로 만들지 않는다. 실제 안전 조건을 입증하지 못하면 Resume는 HOLD다.
범위가 안전하게 격리되지 않으면 전용 시험 환경안을 별도로 비교하며 공유 서울 서비스로 강행하지 않는다.

현재 `live_test_ready=false`, ReplicaLag 기존 FAIL·필수4 NOT_VERIFIED·DR HOLD 유지.
새 read-only 관측은 이전 FAIL을 해소하지 않으며 RDS 승격/DNS/오사카 활성화/Slack/전체 DR 실행을 수행하지 않았다.

## 후속: 후보 게시·실제 SQL 사전 조회 (2026-11-23)

위 표는 최초 읽기 전용 준비 스냅샷이다. 이후 사용자 승인에 따른 후보 게시·키 준비·관리 EC2 도구 준비는
[별도 실행 기록](../../evidence/LBT-60/2026-11-23-candidate-publication/AUDIT.md)과 구분한다.

- 앱 source `be4d0ba`를 고정한 격리 빌드 후 별도 불변 ECR `backend-dr196-trial`에 게시했다. 기존 `backend` 저장소의
  serving tag와 15개 이미지 수명주기에는 쓰지 않았다. main·PR196 merge/push나 GitOps 배포는 하지 않았다.
  격리 빌드 브랜치에는 빌드 workflow를 게시했다. 게시 자체는 Pod 실행이나 실환경 기능 시험 완료가 아니다.
- 첫 후보의 실제 ECR 검사에서 zlib1.3.2-r1/CVE-2026-4738 Critical1건이 나왔다. 첫 digest는 배포 인수하지 않는다.
  앱·migration 소스는 고정하고 별도 runtime Dockerfile의 패키지 명령만 수정한 후보 재빌드·재검사 기록을 확인한다.
  해당 패키지 변경은 격리 workflow override이며, 현재 PR196 Dockerfile에 반영됐다고 해석하지 않는다.
  교체 후보는 zlib1.4-r0, ECR Basic 검사 COMPLETE/검출0건으로 확인했다. 사용 후보는
  `299311846289.dkr.ecr.ap-northeast-2.amazonaws.com/backend-dr196-trial@sha256:f3aa162b6cd5b28028c1681fb1daadffc73351b5e2785f0c7fb8ebd5a25b9469`다.
  교체 빌드 원본은 [45113446633](https://github.com/ktcloud4-SL/labbit-app/actions/runs/45113446633)이며 실제 배포는 미실행이다.
- 로컬 보호 디렉터리에 서로 다른 승인/관측 Ed25519 키를 생성하고 후보의 보호 파일 읽기·공개키 왕복 검증을 통과했다.
  개인키는 저장소/Evidence에 넣지 않았다. 실행 Policy 활성화·승인 발급·클라우드 등록은 미실행이다.
- 관리 EC2 역할의 DSN Secret 권한 부족은 별도 기록했다. 역할을 확대하지 않고 기존 admin3와 SSM 터널로 실제 SQL을
  읽었다. DB 신원·TLS1.3·transaction_read_only=on·ROLLBACK을 확인했고, 적용1–11의 체크섬11/11이 후보 Git과 일치했다.
  12–15는 미적용이며 Worker 제어 테이블5개가 없다. 이 관측은 단일 Writer나 기존 작업 정산 근거가 아니다.
- 첫 자동 세션 종료 확인은 실패해 원본 결과를 NOT_VERIFIED로 보존했다. 후속 exact-session 종료 후 History=Terminated,
